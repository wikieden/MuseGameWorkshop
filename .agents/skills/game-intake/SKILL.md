# Game Intake

## Use When

- A user brings a vague game idea, mechanic, theme, reference, or genre direction.
- A project needs its target player, player fantasy, engine assumptions, and production risks clarified.
- A dry run needs a compact intake record before moving into core-loop design.

## Do Not Use When

- The game direction is already approved and the task is only implementation.
- The user is asking for asset review, engine mapping, or playtest analysis.
- The request is a pure documentation edit with no game-production decision.

## Inputs

- One-line idea or pitch.
- Target audience and locale.
- Reference games or genre anchors.
- Preferred engine or platform, if any.
- Team size, timebox, and constraints.

## Outputs

- One-sentence pitch.
- Player fantasy.
- Target platform and engine assumptions.
- Core production risks.
- Next recommended workflow skill.

## Workflow

1. Restate the idea in game-industry language.
2. Identify the player fantasy, primary verb, and target experience.
3. Ask only for missing decisions that block the next step.
4. Separate confirmed facts from assumptions.
5. Identify the smallest verifiable next output.
6. Recommend `core-loop` or `mechanic-spec` as the next skill.

## Quality Bar

- The output is short enough for a Producer or Game Designer to review quickly.
- The game direction is specific enough to test, not only inspiring.
- Assumptions, risks, and unknowns are visible.
- No game code, asset import, or project structure change is proposed without a design summary, execution plan, impact scope, and approved review gate.

## Common Failure Modes

- Expanding the idea into a full game scope too early.
- Hiding uncertainty behind confident genre labels.
- Describing content quantity instead of player experience.
- Skipping the next smallest verifiable output.
