# Production Target Contract / 生产目标合同

版本：v0.9.3

语言：中文

## 1. 目的

v0.9.3 为 Muse Game Workshop 增加 Production Target Contract / 生产目标合同。它要求团队分别声明 First Playable Target / 首个可玩版本目标与 Final Production Target / 最终生产目标，并把从策划规格到可发布构建的责任、证据和交接边界写清楚。

Muse 支持以下最终生产交付方向：

- Three.js WebGPU Web Runtime / Three.js WebGPU 网页生产运行时。
- Unity。
- Unreal Engine。
- Godot。

Three.js 是正式的 Web 生产运行时，不是只能用于原型的次级选项。它与完整游戏引擎的能力边界不同，但只要项目满足浏览器兼容、性能、可访问性、资产来源和发布验收要求，就可以成为最终生产目标。

## 2. 两个目标必须分开声明

| 决策 | 要回答的问题 | 允许的结果 |
|---|---|---|
| First Playable Target / 首个可玩版本目标 | 用什么运行时最快、最可靠地验证核心体验？ | Three.js、Unity、Unreal、Godot，或经 review 批准的其他轻量验证环境。 |
| Final Production Target / 最终生产目标 | 玩家最终会在哪个运行时和平台获得可发布产品？ | Three.js Web、Unity、Unreal 或 Godot。 |

两个目标可以相同，也可以不同，但不得用“以后再决定”隐藏迁移成本。若目标不同，Review Gate / 评审门必须批准一份 migration plan / 迁移计划，说明哪些内容可直接保留、哪些需要重写、何时停止在首个可玩版本目标上继续扩展。

首个可玩版本通过不等于最终生产目标通过。最终生产目标必须独立完成构建、性能、平台、资产、QA 和发布证据。

## 3. 目标选择记录

每个项目至少记录：

- 项目名称、当前制作阶段和合同负责人。
- 首个可玩版本目标、选择理由和退出条件。
- 最终生产目标、目标平台、输入设备和发布渠道。
- 团队技能、预算、时间、内容规模和性能约束。
- 两个目标之间的共享边界与迁移风险。
- 需要 Producer / 制作人、Technical Lead / 技术负责人、QA / 测试和 Release Manager / 发布负责人的决策。
- 决策日期、review 状态和替代方案。

## 4. Production Target Contract 必填面

| 合同面 | 必须定义 | 首个可玩版本证据 | 最终生产证据 |
|---|---|---|---|
| Inputs / 输入 | 动作表、设备、重绑定、焦点丢失、触控/手柄/键鼠边界 | 核心动作可执行 | 目标设备矩阵、可访问性和重绑定验收 |
| Simulation / 模拟 | 状态、时钟、暂停、随机种子、存档边界、确定性要求 | 核心循环与失败/重试可验证 | 长时运行、恢复、版本迁移和关键回归通过 |
| Data / 数据 | schema、可调参数、配置所有权、序列化和版本规则 | 关键参数不硬编码在热路径 | 数据迁移、校验、兼容和内容构建流程通过 |
| Assets / 资产 | 格式、导入/加载、预算、license、provenance、替代与降级 | 占位资产可读并有来源记录 | 最终资产通过视觉、性能、权利和平台披露检查 |
| UI / 用户界面 | HUD、菜单、设置、分辨率、缩放、输入导航、本地化和可访问性 | 关键流程可完成 | 完整用户流程、目标分辨率和输入方式通过 |
| Platform / 平台 | OS、浏览器或主机、图形能力、存储、网络、隐私和生命周期 | 指定验证环境可运行 | 支持矩阵和不支持矩阵均有真实设备/环境证据 |
| Tests / 测试 | 单元、集成、运行时、视觉、性能、兼容和回归层级 | 核心机制测试与试玩清单 | 发布候选构建通过全套目标平台验收 |
| Package / 打包 | 版本、构建配置、环境变量、依赖锁定、签名/托管、回滚 | 可重复生成测试构建 | 可追溯的 release candidate / 发布候选包 |
| Evidence / 证据 | 命令、日志、测试结果、截图/录像、性能数据、人工决定 | 能证明“可玩” | 能证明“可发布”，并记录未通过项 |
| Handoff / 交接 | 负责人、输入、输出、阻塞项、下一阶段和回退方案 | 策划到实现与试玩交接清楚 | 开发、QA、发布与维护责任清楚 |

## 5. 共享规格与目标适配

引擎无关规格应保留玩家体验和规则真源：

- 核心循环、玩家动词和成功/失败条件。
- 状态转换、事件、参数、数据所有权和存档语义。
- 反馈意图、UI 流程、相机要求和可访问性目标。
- 测试场景、可观察结果和性能预算。

目标适配层负责把这些规格映射到 Three.js、Unity、Unreal 或 Godot 的工程结构。不得把某个引擎类名、Scene/Node/Actor/MonoBehaviour 结构反向当成共享设计真源。

## 6. 首个可玩版本到最终生产的交接

当两个目标不同时，交接包必须包含：

1. 已验证的玩法假设和未解决问题。
2. 状态机、参数表、数据 schema 和参考测试。
3. 输入、UI、相机、音频和反馈行为记录。
4. 可复用资产清单，以及格式、license、provenance 和导入差异。
5. 不能移植的运行时代码和替换方案。
6. 视觉基准、试玩录像、性能基线和已知偏差。
7. 迁移负责人、里程碑、停止条件和回退方案。

迁移验收以行为和证据为准，不以目录或 API 名称相似为准。

## 7. Review Gate 与阶段门

| Gate | 必须回答 |
|---|---|
| Target Selection Gate / 目标选择门 | 为什么选择这两个目标？能力、成本和迁移风险是否可接受？ |
| First Playable Gate / 首个可玩版本门 | 核心体验是否已经通过可重复测试和人工试玩？ |
| Production Entry Gate / 正式制作门 | 最终目标架构、内容管线、平台矩阵和预算是否可执行？ |
| Release Candidate Gate / 发布候选门 | 构建、兼容、性能、资产、可访问性、披露和回滚证据是否完整？ |

任何 AI coding tool 或 editor automation 都不能代替人类 review owner 的批准。

## 8. v0.9.3 范围与交付物

v0.9.3 覆盖：

- 首个可玩版本目标与最终生产目标的分离合同。
- Three.js、Unity、Unreal 和 Godot 的最终生产目标地位。
- 输入、模拟、数据、资产、UI、平台、测试、打包、证据和交接字段。
- Three.js Web production runtime / 网页生产运行时工作流。

v0.9.3 交付物：

- `production-target-contract.zh.md` 与 `production-target-contract.en.md`。
- `threejs-web-runtime.zh.md` 与 `threejs-web-runtime.en.md`。

v0.9.3 不批准：

- 创建或迁移任何游戏项目。
- 选择某个项目的实际最终目标。
- 商业托管、商店提交、主机认证或生产部署。
- 新资产生成、最终资产导入或权利批准。
- 真实 telemetry service / 数据埋点服务。

## 9. 验收标准

v0.9.3 在以下条件满足时通过文档验收：

- 中英文文档语义配对。
- 合同明确区分首个可玩版本目标和最终生产目标。
- Four-target / 四目标支持包含 Three.js WebGPU、Unity、Unreal 和 Godot。
- 十个合同面均包含最低字段和证据要求。
- Three.js 被定义为正式 Web 生产运行时，并具有独立发布门。
- 禁止范围和人工 review 责任清楚。

## 10. v0.9.4 与下一版本

v0.9.4 在本合同上增加 Unity Workflow / Unity 工作流，并保持 Unity 6、项目版本记录、测试、构建和 editor-evidence 边界一致。

v0.9.3 与 v0.9.4 完成后，下一计划版本仍为 v0.10 Telemetry & Playtest Analytics / 数据埋点与试玩分析。v0.10 可以复用本合同的事件、平台、构建和证据字段，但不得把真实用户数据服务倒灌进 v0.9.3 或 v0.9.4。
