| Decision | Recommended Decision | Impact |
|---|---|---|
| Should v0.1 only materialize the workflow pack? | Yes | Prevents the example game from swallowing the product. |

| Should Boss Rush run as a no-code dry run first? | Yes | Validates the workflow without starting game implementation. |

The review gate has only three valid statuses:

- `Approved`: v0.1 implementation may proceed according to this document.
- `Needs revision`: revise this document or the manifest, then review again.
- `Rejected`: stop v0.1 implementation and revisit direction.

## 4. Execution Principles

1. Review first: every structural, code, or asset change starts with a design summary and execution plan.
2. Workflow first: v0.1 delivers rules, skills, templates, checks, and dry-run evidence.
3. Tool-agnostic: Codex, Claude Code, Kiro CLI, opencode, and similar tools should read the same rules.
4. Game-industry language first: public-facing names use recognizable production language such as Concept, Pre-production, Prototype, Vertical Slice, Playtest, QA, and Release.
5. Preserve AI-native evidence: prompts, tools, licenses, reviews, test results, and decision records must be file-backed.
6. Bilingual-ready: Chinese docs use Chinese game-industry terminology; English docs use natural English production language.
7. No premature game code: the Godot playable prototype starts in v0.2.

## 8. Test Method

v0.1 testing has four layers.

### 8.1 Documentation Tests

- All local Markdown links in README and docs exist.
- All core docs exist in Chinese and English pairs.
- Startup prompts include `overall project plan`, `v0.1 execution plan`, `P0 skill skeleton plan`, `v0.1 manifest`, `testing strategy`, `bilingual audience strategy`, and the review gate.

### 8.2 Skill Contract Tests

Every skill must pass these manual or scripted checks:

- It has `Use When` and `Do Not Use When`.
- It has clear `Inputs`, `Outputs`, `Workflow`, and `Quality Bar`.
- A skill that changes project structure, code, or assets requires a design summary and execution plan first.
- Outputs return to templates or evidence files instead of remaining only in chat history.

### 8.3 Template Tests

Every template must:

- Start with the shared metadata block.
- Include `Language`, `Target Audience`, `Locale`, `Terminology Source`, `Owner`, and `Review Status`.
- Avoid depending on a single AI coding tool or a single engine.
- Be understandable through the matching Chinese or English docs.

### 8.4 Dry Run Tests

The Boss Rush / Counter Trial dry run must prove:

- The AI tool reads docs and rules first.
- The AI tool outputs a design summary, execution plan, impact scope, and review points before modifying files.
- No game code is written.
- The pitch can become a core loop, mechanic spec, engine mapping, and playtest plan.
- The review gate record has a clear status.

## 9. Key Risks And Controls

| Risk | Symptom | Control |
|---|---|---|
| Premature game implementation | v0.1 contains runnable Godot/Unreal code | Block with `check-v0.1-manifest` and the review gate. |
| Skills sound like unfamiliar agent taxonomy | Game-industry users cannot understand the workflow | Map skill names and descriptions to production stages, disciplines, and deliverables. |
| Chinese and English docs drift | English docs miss read items or Chinese docs miss terminology mapping | Use doc-pair checks, startup-prompt checks, and glossary checks. |
| Templates become too heavy | Indie developers avoid using them | Keep templates short, copyable, and fillable in 10-20 minutes for a first pass. |
| Creative AI assets bypass review | Assets exist without source or license records | Require asset brief, provenance, and review records. |
| Tool binding happens too early | Workflow only works in Codex or one specific tool | Keep tool adapter rules as mappings; do not bind the workflow to one tool. |
